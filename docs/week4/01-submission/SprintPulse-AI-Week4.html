1. Evaluation framework and evidence boundaries

This project evaluates an existing Python Streamlit and LangGraph sprint assistant; it does not rebuild the application. The agent retrieves synthetic Jira-style snapshots, computes deterministic metrics/risks/history, and generates answers or approval-gated report drafts. Current snapshot facts take precedence over historical context.

The evaluation executes the real graph, records node callbacks and nested tool calls, and separates final requests from scenario setup turns. The callback path is recall_conversation → route_request → evidence node → remember_findings → answer/report. Tools are existing route-specific bundles, not newly learned dynamic planning.

Dataset and source-grounded expectations

  • Golden v1: 40 cases: 20 happy paths, 12 edge cases, 6 known routing failures and 2 adversarial cases.
  • Holdout v1: 14 separately reviewed/frozen G01–G14 cases with renamed-ID, zero-point, partial-evidence, memory, recovery and adversarial fixtures.
  • Expectations were checked against actual CSVs, deterministic tools, independent arithmetic and documented behavior. Six initially partial golden intent labels were explicitly reviewed before freeze. No expected answer came from an agent prediction.

3. Failures, improvements and generalization

Three significant failure categories

  1. Lexical intent-routing gaps: weekly summaries, impediments, delivery rates, completed items, historical risk changes and side-by-side comparisons were misrouted. Narrow aliases and existing precedence were preserved; golden routing rose from 34/40 to 40/40.
  2. Evidence-to-answer omissions: tools returned correct data, but generic fallback prose omitted requested IDs, points remaining, overdue detail, durations and dated current/historical distinctions. A deterministic grounded renderer increased golden correctness from 20/38 to 38/38.
  3. Boundary and scope errors: unseen fixtures exposed confusion between unfinished and overdue, missing predecessors, and hard-coded ticket prefixes. These remained despite 100% golden scores.

What generalized—and what did not

The original holdout supports transfer of initial routing improvements to new phrasings and fixtures:14/14 routes, improved vs10/14 baseline. Correct-answer completeness generalized only partially:11/14, below the95% goal. Correct routing and tool data did not guarantee correct scoped answers. The final14/14 demonstrates closure of the known gaps only. No new holdout was generated; further unseen testing needs separate review and freeze.

Limitations

  • Full-dataset grades remain provisional;15sampled judgments have author review only.
  • Local checkpoint tests do not certify production storage durability, per-user authentication or hosted mem0 retrieval.
  • Lexical routing, supported sprint naming and sparse ticket-status evidence remain bounded; broad adversarial/live-model resilience is untested.
  • No paid inference, tracing, hosted mem0, production DB access or deployment change occurred in this submission preparation. Existing deployment is untouched.

Key learnings and demonstration

  1. Ground truth must come from verified sources—not agent predictions.
  2. Measure routing, evidence retrieval and answer sufficiency separately.
  3. Holdouts reveal scope defects that a tuned golden suite can miss.
  4. Preserve failures, denominators and original results; remediation is not unseen evidence.
  5. Privacy, budget admission and human approval are evaluation requirements.
